# AI usage

How PULSE uses generative AI, as required by the SOEN 490 Code Quality Rubric
(section 8). Every team member adds their own tools, features and examples here.

## How we declare AI contribution

- **Source files:** every source file starts with one of these lines (`//` in
  TypeScript):

  ```python
  # AI contribution: No substantial AI-generated code
  # AI contribution: Below 50% AI-generated
  # AI contribution: 50% or more AI-generated
  ```

  The level is the author's good-faith estimate for the file as it is now. Code
  first generated by AI counts as AI-generated even after we edit it. Autocomplete
  and syntax suggestions do not count.
  `python scripts/ai_declarations.py` checks this in pre-commit and CI.
  Files still waiting for their author's estimate are listed in
  `scripts/ai_declarations_pending.txt`. Add the line with
  `python scripts/ai_declarations.py --add <none|below-50|50-or-more> FILE`, then
  remove the file from that list.
- **Pull requests:** the "AI assistance" section of the PR template gives the
  level for the code in the PR and lists the AI-assisted files.
- **Commits:** commits that an AI tool helped with end with an `AI-assisted: ...`
  line.

Covered files: Python in `backend/app`, `backend/synthetic`, `backend/tests`,
`discord-bots` and `scripts`, and TypeScript in `frontend/src`. Alembic
migrations, empty `__init__.py` files and `vite-env.d.ts` are excluded.

## Details

### Omerlo backoffice API client and connector (#70, #71)

Claude Code wrote the HTTP client from the Omerlo backoffice API
documentation. It covers the `x-api-key` header, the error types for 401, 403
and 404, and cursor pagination. The connector built on it lists records newest
first and stops at the last sync's watermark. Claude Code also wrote the
client and connector tests against a mocked transport. I chose the API (the
backoffice one rather than the Reader API) and the watermark rule, and
reviewed the code.

**Verification:** `tests/ingestion/omerlo/` covers pagination, the watermark
stop and each error status, and teammates reviewed both PRs.

**Problem found:** while resolving a rebase conflict, Claude Code kept the old
Reader API settings block in the commit that introduced the API key. I caught
it while reviewing the commits and folded the fix into that commit.

### Versioned source records (#123)

Claude Code wrote the versioned upsert. A changed record closes the current
version (`valid_to`) and opens a new one. An unchanged record, detected by
content hash, is left alone. It also wrote the query for the version valid at
a given run, and the migration that adds the content hash and the removal
marker.

**Verification:** the integration tests in
`tests/integration/test_source_records.py` run on Postgres and check that
re-running the same payloads creates no new version. They also rely on the
`ex_source_record_versions_overlap` constraint, which rejects overlapping
versions.

**Correction:** the generated "latest version" query used
`Select.distinct(column)`, the PostgreSQL `DISTINCT ON` form that SQLAlchemy
deprecates. It now uses `.ext(distinct_on(...))`, which SQLAlchemy recommends
instead.

### Change detection between sync runs (#125)

Claude Code wrote the field-level diff between two versions of a record. It
also wrote `record_changes`, which stores what each sync run added, modified
or removed, and `diff_runs`, which compares any two runs.

**Verification:** `tests/test_fixture_diff.py` checks the diff of the mapped
fixtures against `expected_diff.demo.json` from the mutation script (#124).
The integration tests check each change type on Postgres.

**Problem found:** `diff_runs` built its id map with `dict(result.tuples())`,
which fails on the result type SQLAlchemy returns there. It now reads the rows
one by one. The same mistake came back in #127 (below).

### Recorded incremental sync runs (#126)

Claude Code wrote the sync run service: one `sync_run` row per run, with a
watermark per workspace, the counts and the error. It also wrote the retry
transport, which uses exponential backoff on network and 5xx errors, and the
`app.sync` command.

**Verification:** the unit tests mock the connector. The integration tests run
a full sync and then an incremental one against the mock server's fixtures. I
also ran it on a local Postgres. The full sync stored 560 records, and after
the demo mutation set the incremental sync reported 5 added and 9 modified
records, matching the expected diff.

### Sync runs page (#127)

Claude Code wrote the read-only endpoints (runs, a run's changes, record
search, a record's version history) and the React page that shows them.

**Verification:** `tests/api/test_browse.py`,
`tests/integration/test_browse_api.py` and `SyncRunsPage.test.tsx`. I also
checked the page by hand after a real sync.

**Problems found:**
- The history endpoint crashed with a `TypeError`: the generated code called
  `dict()` on a SQLAlchemy result. I found it by clicking through the page, and
  fixed it with a dict comprehension.
- The generated page reset its state inside effects, which our ESLint rules
  reject (`react-hooks/set-state-in-effect`). I moved the resets into the event
  handlers.
- The generated test for a bad `kind` expected a 422 but got a 503, because
  FastAPI resolves the database dependency before validating the query. The
  test now overrides the dependency.

### CSV and JSON file import (#24)

Cursor's agent proposed the design and wrote the code and tests in eight
commits: a reader interface so `run_sync` is no longer tied to Omerlo, the
shared cleaning step, the CSV and JSON reader, row validation and mapping, the
archive of the whole file (with migration 0007), the `app.import_file` command,
and the end-to-end tests. I chose the behaviour on re-import (missing rows are
only removed with `--full`) and kept the scope to a command, with the upload
endpoint and screen left for later.

**Verification:** unit tests in `tests/ingestion/files/`, `run_sync` tests with
the file reader in `tests/services/test_sync_runs.py`, and integration tests on
Postgres in `tests/integration/test_file_import.py` and
`tests/integration/test_import_command.py` (changes on re-import, removal with
`--full`, tenant isolation, 5,000 rows in about 3 seconds). I also imported the
sample files in `synthetic/samples/` by hand.

**Problems found during the design:**
- `source_record` ids are only unique per source, not per kind, so an
  organization and a person with the same id in one csv source would have
  collided. Import ids are prefixed with their kind (`organization:42`).
- A full import of an organizations file would have marked every person of the
  same source as removed. `close_unseen()` now only removes the kinds the run
  read.
- Once a tenant had a csv source, `app.sync` would have stopped with "several
  sources". It now only looks at Omerlo and mock sources.

**Problem found:** the first command tests read the JSON log lines on stdout
as the command's output. They now filter them out, as the sync command tests
do.
